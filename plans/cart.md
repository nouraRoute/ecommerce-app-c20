# Cart Plan (domain + data only)

## 1. Opinion
Well-defined: four actions on a new `cart` feature, built with `FEATURE_STRUCTURE.md`. All four endpoints answer with one wrapper shape (status, message, numOfCartItems, cartId, data), so one shared `CartResponseModel` replaces four identical per-action wrappers (deviation from the one-wrapper-per-action rule, by decision). The cart's product object is a subset of what `ProductResponseModel` already parses, so it and `ProductEntity` are reused; the cart line (count, price, product) gets its own `CartItemEntity`. Inputs below were captured from the live server with a throwaway account on 2026-11-04.
**Risks:** `POST /cart` returns `product` as an id string while GET/PUT/DELETE return the populated object; `CartItemResponseModel` has a custom `fromJson`, so the add response maps to a `ProductEntity` with only `id` set and the screen must call `getCart` for titles and images · the token is sent as a `token` header read from `SharedPreferences` inside `CartRepoImpl` (no Dio interceptor yet, per plan); logged-out calls come back as a `Failure` with the server's 401 message · `numOfCartItems` counts lines, not units · the cart product omits `price`, `description`, `images`; the unit price is `CartItemEntity.price` · `PUT`/`DELETE` for a product not in the cart return 500/404 with a message, surfaced as a `Failure` · `di.config.dart` is regenerated by build_runner.

## 3. Architecture
`GetCartUsecase` / `AddToCartUsecase` / `UpdateCartItemUsecase` / `RemoveFromCartUsecase → CartRepo → CartRepoImpl → CartDataSource → CartApi → Dio`, mirroring `products`. `CartRepoImpl` also takes `SharedPreferences` (like `AuthRepoImpl`) to read the stored token and passes it down as a plain `String`; the API methods take `@Header('token')`. Wrapper: `CartResponseModel` (owns `toDomain()` because the entity flattens `numOfCartItems` with `data.*`). Nested: `CartDataResponseModel` (the `data` object), `CartItemResponseModel` (owns `toDomain()` → `CartItemEntity`, polymorphic `product`), reused `ProductResponseModel` and its children. Request models: `AddToCartRequestModel`, `UpdateCartItemRequestModel`. `CartEntity.items` is non-null (`const []` default) so the screen never null-checks the list.

## 6. Handoff
`GetCartUsecase.call()` · `AddToCartUsecase.call(String productId)` · `UpdateCartItemUsecase.call(String productId, int count)` · `RemoveFromCartUsecase.call(String productId)`, all → `Response<CartEntity>` holding the cart as it is after the call; all registered in DI. Gate cart screens on `CheckLoginUsecase` first. Use `numOfCartItems` from the add response for a badge and reload with `getCart` to render the list. `DELETE /cart` (clear cart) is not wired yet.
