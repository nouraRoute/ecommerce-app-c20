# Category Plan (domain + data only)

## 1. Opinion
Well-defined: two GET actions on one new `category` feature, built with `FEATURE_STRUCTURE.md`. Both return list wrappers of the same shape (results, metadata, data), and both items map to the single `CategoryEntity` (by decision). Scope stops at the domain boundary; the existing categories tab under `main_layout/categories/presentation` is wired in a separate presentation plan.
**Risks:** subcategory items have no `image` and carry a parent `category` id, so they get their own `SubcategoryResponseModel`; `CategoryEntity.image` is null for subcategories and `SubCategoryItem` must handle that · the sample subcategory response mixes several parent `category` ids, which looks like `GET /subcategories` (all) rather than one category's children; the endpoint stays `/categories/{id}` as specified, so confirm it against the server · entity holds only `id`, `name`, `image`; `slug` and `category` stay in the response models until a screen needs them · `di.config.dart` is regenerated, so stale generated files will not compile until build_runner runs.

## 3. Architecture
`GetCategoriesUsecase` / `GetSubcategoriesUsecase → CategoryRepo → CategoryRepoImpl → CategoryDataSource → CategoryApi → Dio`, mirroring `auth` method-for-method. Wrappers: `GetCategoriesResponseModel` (results, metadata, data: categories) and `GetSubcategoriesResponseModel` (results, metadata, data: subcategories). Nested: `CategoryResponseModel` and `SubcategoryResponseModel` (each owns `toDomain()` → `CategoryEntity`), shared `MetadataResponseModel`.
