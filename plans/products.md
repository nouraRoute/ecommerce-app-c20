# Products Plan (domain + data only)

## 1. Opinion
Well-defined: one GET action on a new `products` feature, built with `FEATURE_STRUCTURE.md`. The list wrapper has the same shape as categories (results, metadata, data), so `MetadataResponseModel` is reused. The product's nested `category` and `subcategory[]` objects are the same shapes the category feature already parses, so `CategoryResponseModel` / `SubcategoryResponseModel` and the existing `CategoryEntity` are reused (by decision). `brand` is the only new sub-entity. All query parameters live on one `ProductsParamsEntity` (Equatable + `copyWith`) so the presentation layer can hold and tweak the current filter as a single value.
**Risks:** `copyWith` cannot reset a filter back to null (standard `??` pattern); clearing a filter means building a new `ProductsParamsEntity` · `price` and `ratingsAverage` are `num?` since the server may return decimals · the response carries both `_id` and `id`; the model maps `_id` and ignores `id` · `slug`, `createdAt`, `updatedAt` stay in the response model until a screen needs them · `di.config.dart` is regenerated by build_runner.

## 3. Architecture
`GetProductsUsecase → ProductsRepo → ProductsRepoImpl → ProductsDataSource → ProductsApi → Dio`, mirroring `category`. The repo impl unpacks `ProductsParamsEntity` into named `@Query` arguments; Retrofit drops nulls and Dio's default `ListFormat.multi` emits one `category[in]=` pair per id. Wrapper: `GetProductsResponseModel`. Nested: `ProductResponseModel` (owns `toDomain()`), `BrandResponseModel` (owns `toDomain()`), reused `CategoryResponseModel`, `SubcategoryResponseModel`, `MetadataResponseModel`.

## 6. Handoff
`GetProductsUsecase.call([ProductsParamsEntity params])` → `Response<List<ProductEntity>>`; registered in DI. Omit `params` for the unfiltered first page; pass `const ProductsParamsEntity(limit: 20, sort: '-price')` etc. to filter, and `params.copyWith(page: 2)` to page.
