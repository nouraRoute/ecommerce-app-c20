# Register Plan (domain + data only)

## 1. Opinion
Well-defined: the signup contract has the same shape as login, so this is a second action on the existing `auth` feature, not a new one. Scope stops at the domain boundary per `FEATURE_STRUCTURE.md`; the cubit, states and `SignUpScreen` wiring are a separate presentation plan. `UserEntity` stays untouched: `rePassword` is not a domain field, so `RegisterRequestModel.fromDomain()` sends `password` twice. Display fields are `name` and `email` only (same as login; `role` stays in the response model by decision), so `UserResponseModel.toDomain()` is reused as is. Token handling is deferred by decision; the wrapper still parses it so nothing is lost later.
**Risks:** mirroring `rePassword` makes the server's match check a no-op, so the confirm-password check must live in the form (presentation plan) · `register_usecase.dart` is already committed as an empty file and must be filled, not re-created · `auth_api.g.dart` and `di.config.dart` are regenerated, so stale generated files will not compile until build_runner runs.

## 2. Proposed Architecture
Add a `register` action through the existing `auth` chain: `RegisterUsecase → AuthRepo → AuthRepoImpl → AuthDataSource → AuthApi`, mirroring `login` method-for-method. One new request model and one new response wrapper; the nested `UserResponseModel` and `UserEntity` are shared with login. The use case returns `Response<UserEntity?>` exactly like `LoginUsecase`, so the presentation plan consumes both the same way.
**Alternatives rejected:**
- Reuse `LoginResponseModel` for signup: identical JSON today, but the name lies and couples two endpoints; the doc says one wrapper per action.
- Add `rePassword` to `UserEntity`: rejected by decision; it is a form concern, not a user property.
- Pass `rePassword` as a second use-case parameter: breaks the `call(UserEntity)` symmetry with login for no domain gain.

## 5. Components
- **Domain:** `UserEntity` (existing, unchanged: name, email, password, phoneNumber) · `AuthRepo.register` · `RegisterUsecase`: `call(UserEntity)` → `Future<Response<UserEntity?>>`
- **Data:** `RegisterRequestModel` (name, email, password, rePassword, phone; `fromDomain` sets `rePassword: user.password`, `phone: user.phoneNumber`) · `RegisterResponseModel` (message, user, token; nests existing `UserResponseModel`) · `AuthRemoteDataSource.register` · `AuthRepoImpl.register` → `responseModel.user?.toDomain()`
- **API:** `POST /auth/signup` (new): create account, returns user + token · `POST /auth/signin` (existing, untouched)
- **Presentation:** out of scope. Handoff: `RegisterUsecase` in DI + shared `UserEntity`; cubit, states and screen wiring go in the presentation plan.
- **DI:** `RegisterUsecase` `@injectable` · `dart run build_runner build --delete-conflicting-outputs` then `flutter analyze` · confirm `di.config.dart` lists `RegisterUsecase`
